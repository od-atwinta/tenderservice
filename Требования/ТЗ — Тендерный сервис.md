## 1. Общее

### 1.1. Цель

Перевести тендерную работу Атвинты из Google-таблицы, Telegram-тем и
облачных папок в один сервис: от выгрузки тендера до итога, со статистикой
для руководства.

Сейчас процесс живёт в таблице «Тендеры» (≈2 500 строк за 2026 год, листы
«Тендеры», «Ответы», «статистика»), отчёты нейронки — отдельными
Google-документами, обсуждение — в Telegram, документы — на Google/Яндекс
Диске. Статистика считается вручную.

### 1.2. Проблема и результат

**Проблема.** Данные о тендерах разбросаны по таблице, документам, чатам и
дискам; статистику (подачи, переторжки, основные этапы, выигрыши) менеджер
собирает вручную в листе «статистика» и сверяет с другими листами. На сверке
данных за 2026 год ручной подсчёт разошёлся с фактическими строками таблицы
на несколько подач. HTML-макеты с реальными данными упираются в память
браузера и не могут быть открыты команде.

**Результат первой очереди** считается достигнутым, если:

| Метрика | Цель |
|---|---|
| Где ведутся тендеры | все новые тендеры и решения по ним — только в сервисе, таблица не заполняется |
| Статистика подач | дашборд за любой период строится без ручного подсчёта и совпадает с контрольными цифрами 7.4 |
| Доступ команды | каждый сотрудник входит под своим логином и видит тендеры по своим правам |
| Скорость работы | списки и дашборд на полном объёме данных открываются в сроки из раздела 12 |

### 1.3. Пользователи

| Кто | Что делает в сервисе | Системная роль |
|---|---|---|
| Менеджеры отдела продаж | ведут тендеры, принимают решения, меняют статусы, готовят подачу | Менеджер (часто вместе с Админ/Суперадмин) |
| Специалисты направлений | изучают документацию, готовят техническую часть | Сотрудник отдела, Руководитель отдела |
| Руководство компании | смотрят аналитику, выгружают отчёты | Наблюдатель |

Юристы, бухгалтерия и замдиректора (ЭЦП, ЭДО) пользователями сервиса не
являются.

### 1.4. Входит в сервис

- весь цикл тендера: появление → первое решение → изучение → второе решение →
  подготовка → подача → после подачи → переторжка/этапы → итог;
- многоэтапные тендеры (НДА, ПКО, Основной, Этап 2/3, Переторжка, RFI);
- дашборд и статистика по подачам;
- справочники и пользователи с ролями;
- Копилка документов (учредительные, опыт, штат, шаблоны, библиотека файлов);
- чат внутри тендера, события после подачи, журнал действий (логи);
- чек-лист документов и задачи с ответственными и сроками;
- уведомления в сервисе;
- календарь сроков;
- платежи площадок (тарифы и обеспечение);
- интеграции: выгрузка тендеров и отчёт ИИ, Checko, Jira (в перспективе).

### 1.5. Не входит

- гранты;
- ИИ-чат-боты как отдельное направление из таблицы;
- статистика по затраченным часам (изучение, подготовка);
- внешние облачные хранилища (Google Диск, Яндекс Диск) — документы в Копилке;
- документооборот с юристами и бухгалтерией (остаётся во внешних ресурсах).

### 1.6. Словарь

| Термин | Значение |
|---|---|
| Раздел | место тендера в меню: Новые, Ожидают решения, В работе, Заявки, Архив |
| Решение об участии | участвуем / отказ / на рассмотрении |
| Этап тендера (секция) | последовательная часть многоэтапного тендера: НДА, ПКО, Основной, Этап 2, Этап 3, Переторжка, RFI |
| Этап процесса | системная стадия: Отбор, Изучение, Подготовка, Подача, Итог |
| Статус | состояние активного этапа тендера (см. 5.3) |
| Подача | факт отправки заявки по этапу тендера с датой фактической подачи |
| Ответственный (менеджер тендера) | пользователь, который ведёт тендер |
| Участники тендера | сотрудники направлений, добавленные в тендер |
| Направление | отдел: Продвижение, Техническая поддержка, Разработка, Аналитика, Дизайн, Аутстафф, Медботы, Аналитика/ИИ |
| Лот | часть многолотового тендера со своим направлением, НМЦ и итогом; все лоты подаются одной заявкой в одну дату (разные заявки = разные тендеры) |

## 2. Стек и архитектура

### 2.1. Решения

| Слой | Решение | Статус |
|---|---|---|
| Приложение | Next.js (App Router), TypeScript | решено |
| База данных | PostgreSQL | решено |
| Хостинг, домен, резервные копии | разработчики Атвинты | решено |
| Доступ к базе | ORM с миграциями (рекомендация: Prisma или Drizzle) | предложение, выбирают разработчики |
| Интерфейс | компоненты по `Дизайн-система.md`; база — Tailwind CSS + shadcn/ui | предложение |
| Вход | логин + пароль, серверные сессии (рекомендация: Auth.js) | предложение |
| Файлы | S3-совместимое хранилище, в базе — только метаданные и ссылка | предложение |
| Фоновые задачи | очередь заданий на PostgreSQL (рекомендация: pg-boss) или отдельный воркер | предложение |

### 2.2. Принципы

- **Один источник данных** — база. Никаких копий данных в браузере
  (в макетах данные жили в `localStorage`; в сервисе этого быть не должно).
- **Права проверяются на сервере**, а не только скрытием кнопок в интерфейсе.
- **Справочники не удаляются, а деактивируются** (история должна оставаться
  читаемой).
- **Каждое значимое действие пишется в журнал** (кто, когда, что было, что
  стало) — из него строятся вкладка «Логи» и история изменений статусов.
- **Статистика считается из фактов** (этапов с датами подачи), а не из
  текущего статуса тендера.
- **Интеграции изолированы**: выгрузка тендеров и отчёты ИИ приходят через
  отдельный входной API или задачу, сервис не зависит от их внутреннего
  устройства.

### 2.3. Окружения

- разработка, тестовое (с копией реальных данных), рабочее;
- тестовое окружение закрыто входом так же, как рабочее — в нём реальные
  данные.

## 3. Роли и доступы

### 3.1. Роли

| Роль | Кратко |
|---|---|
| Суперадмин | все права без исключений; единственный управляет ролями и доступами; открывает Админам доступ к «Настройкам» |
| Админ | всё, что доступно ролям ниже; «Настройки» — если открыл Суперадмин; назначает пользователям роли; не меняет матрицу прав («Роли и доступы») |
| Наблюдатель | только чтение: дашборд (с настройкой), сводная таблица, все разделы тендеров (Новые, Ожидают решения, В работе, Заявки, Архив) и карточки; может отмечать избранное |
| Менеджер | основной пользователь: работа по тендеру, статусы, этапы |
| Руководитель отдела | как Сотрудник отдела + назначает ответственного из сотрудников своего отдела |
| Сотрудник отдела | работа с документами и процессами по тендеру |

- Роли совмещаются: у пользователя может быть несколько ролей, права
  складываются.
- «Руководитель группы» — не отдельная роль, это Админ.

### 3.2. Видимость тендеров

- Админ, Суперадмин и Наблюдатель видят все тендеры.
- Остальные — тендеры, у которых хотя бы одно направление входит в
  направления пользователя.
- Тендер без направления такому пользователю не виден.
- Ответственный и участники тендера видят его всегда, независимо от
  направлений.

## 4. Модель данных

Сущности первой версии. Поля — логические; типы и индексы определяют
разработчики.

### 4.1. Тендер (`tender`)

| Поле | Описание |
|---|---|
| id | |
| name | название |
| customer | заказчик |
| customer_inn | ИНН заказчика (для Checko) [Решить: источник] |

### 4.4. Правила целостности

- Статус тендера = статус активного (последнего незавершённого) этапа.
- Итоговые статусы (5.3) завершают этап.
- Следующий этап создаётся только после статуса «Допущены» по предыдущему.
- Завершённый этап только для чтения. Исключение — Суперадмин: кнопка
  «Исправить» у завершённого этапа (в том числе у тендера в Архиве) открывает
  этап на правку (срок, дата фактической подачи, сумма, описание); у
  последнего этапа дополнительно правится «Дата итога». Исправление пишется
  в журнал: «Исправлен завершённый этап …: было → стало».
- Ответственный при нескольких направлениях — только менеджер отдела продаж.
- Удаление направления из тендера снимает участников этого направления
  (с подтверждением и записью в журнал).
- Лоты есть только у тендера с признаком «Многолотовый». Направления лотов
  автоматически добавляются в направления тендера.
- Статус тендера «Выиграли» ставится, если выигран хотя бы один лот; если не
  выигран ни один — итоговый статус тендера выбирается как обычно
  (например, «Отклонено»). Результат лотов статус тендера не меняет
  автоматически — его меняет пользователь.

## 5. Жизненный цикл тендера

### 5.1. Процесс

| Шаг | Что происходит | Раздел | Этап процесса |
|---|---|---|---|
| 1 | Тендер появляется: выгрузка (5.6) или «Добавить тендер» | Новые | Отбор |
| 2 | Первое решение: «Взять в работу» (направления + ответственный) или «Отказ» (причина) | → Ожидают решения / Архив | Отбор |
| 3 | Детальное изучение, при необходимости — задача юристам/бухгалтерии | Ожидают решения | Изучение |
| 4 | Второе решение: «Участвуем» или «Отказ» (причина) | → В работе / Архив | Изучение |
| 5 | Подготовка: документы, чек-лист, оплата площадки, оценка трудозатрат | В работе | Подготовка |
| 6 | Формирование КП и пакета документов на подачу | В работе | Подготовка |
| 7 | Подача: статус «Подано», дата фактической подачи | Заявки | Подача |
| 8 | После подачи: события, ожидание ответа | Заявки | Подача |
| 9 | Следующий этап / переторжка — новый этап тендера после «Допущены» | Заявки/В работе | Подготовка/Подача |
| 10 | Итог: выиграли / отклонено / отказались сами / … | Архив | Итог |

### 5.2. Раздел тендера

Раздел вычисляется, не хранится вручную:

1. Решение = «отказ» → **Архив**.
2. Есть статус: ключевой статус → раздел из матрицы 5.3; сквозной — раздел не
   меняется.
3. Нет статуса: решение пусто → **Новые**; «на рассмотрении» → **Ожидают
   решения**; «участвуем» → **В работе**.
4. Активный этап «ПКО» или «НДА» → **В работе** при любом его статусе (в т.ч.
   «Подано»): это предварительный отбор, основная подача ещё впереди
   (решено 18.09.2026). Итоговый статус, как и везде, переводит в Архив.

### 5.3. Статусы

| Статус | Тип | Раздел | Итоговый (завершает этап) | Спрашивает причину |
|---|---|---|---|---|
| На рассмотрении | ключевой | Ожидают решения | нет | нет |
| Оценка | сквозной | Новые, Ожидают решения, В работе, Заявки | нет | нет |
| Формирование заявки | ключевой | В работе | нет | нет |
| Готово к подаче | ключевой | В работе | нет | нет |
| Подано | ключевой | Заявки | нет | нет |
| Допущены | сквозной | Ожидают решения, В работе, Заявки | нет (разрешает следующий этап) | нет |
| Отклонено | ключевой | Архив | да | да |
| Отказались сами | ключевой | Архив | да | да |
| Отменено | ключевой | Архив | да | да |
| Без выбора победителя | ключевой | Архив | да | да |
| Завершено без ответа | ключевой | Архив | да | да |
| Не допущены | ключевой | Архив | да | да |
| Выиграли | ключевой | Архив | да | нет |

Смыслы: «Отклонено» — отказ заказчика; «Отказались сами» — наш отказ после
начала участия; «Завершено без ответа» — в т. ч. RFI без ответа.

Матрица «статус → раздел» редактируется в Настройках → Справочники.

### 5.4. Смена статуса

- Общее окно «Изменить статус» во всех местах (В работе, Заявки, карточка).
- Обычный пользователь видит ключевые статусы текущего и следующего раздела и
  сквозные статусы текущего; Админ/Суперадмин — все.
- Статус с причиной — обязательный выбор причины из справочника + комментарий.
- Если статус переносит тендер в другой раздел — подтверждение «Тендер будет
  перенесён в раздел «…»» (Перенести / Отмена). До подтверждения ничего не
  меняется.
- Смена статуса пишет журнал и отправляет уведомления (9).
- Переход в «Ожидают решения» создаёт ответственному задачу «Изучить
  документы и принять решение по тендеру «…»».
- **Защита от случайной смены статуса** (решено: нужна):
  - перенос в другой раздел — только через окно подтверждения (см. выше);
  - после сохранения 15 секунд показывается уведомление с кнопкой
    «Отменить» — отмена возвращает статус, раздел, дату «Закрыто», этап и
    причину отказа к прежним значениям, а отправленное уведомление участникам
    помечается как отменённое;
  - позже отменить последнюю смену статуса может Админ/Суперадмин из вкладки
    «Логи» с обязательным комментарием; откат тоже пишется в журнал;
  - итоговые статусы (5.3) дополнительно требуют выбрать причину, поэтому
    случайно закрыть тендер одним кликом нельзя.

### 5.5. Возврат из Архива

Только Админ/Суперадмин, кнопка «Вернуть в работу»:

| Выбор | Решение | Статус | Раздел |
|---|---|---|---|
| Новые — отбор | пусто | пусто | Новые |
| Ожидают решения — на рассмотрении | на рассмотрении | На рассмотрении | Ожидают решения |
| В работе — формирование заявки | участвуем | Формирование заявки | В работе |
| В работе — готово к подаче | участвуем | Готово к подаче | В работе |
| Заявки — подано | участвуем | Подано | Заявки |

Обязательно: статус и ответственный; комментарий. Причина отказа очищается.
Журнал + уведомление ответственному «Необходимо ознакомиться с изменениями в
карточке тендера».

### 5.6. Появление тендера

- **Автоматически** — выгрузка и отчёт ИИ (10.1). Тендер создаётся в «Новых»
  с отчётом ИИ, индикатором риска и документами закупки.
- **Вручную** — «Добавить тендер» в шапке любой страницы: название, заказчик,
  НМЦ, ссылка на источник, дата и время подачи, раздел («Новые» по умолчанию
  или «Ожидают решения» → решение «на рассмотрении»). Ответственный не
  назначается. У ручного тендера нет отчёта ИИ — [Решить] запускать ли
  генерацию отчёта для ручного тендера по загруженным документам.
- **Проверка дублей** при создании: по внешнему идентификатору, ссылке и
  похожему названию + заказчику; найденные совпадения показываются
  предупреждением. [Решить] точные правила для автоматической выгрузки.

- Название некликабельно (действие — «Подробнее»).

**Ожидают решения.**
- Карточки; «Перейти в карточку ↗»; «Отказ» (причина) и «Участвовать» → В
  работе.
- Быстрые фильтры: «Только мои», «Избранные».

**В работе.**
- Карточки: статус-бейдж, «Создано», название (ссылка в карточку), заказчик,

**Заявки.**
- Таблица: избранное, название, дата подачи, менеджер, площадка, дата
  ожидания ответа, статус ответа, «Изменить статус».
- Фильтры: источник, менеджер, направление, статус ответа, только избранные,
  поиск; переключатель периода и сводные цифры; выгрузка.

**Архив.**
- Таблица только для чтения: избранное, ответственный, название, статус
  (фактический последний), заказчик, НМЦ, публикация, источник, отчёт,
  окончание сбора, отдел, решение, причина отказа, закрыто, действия.
- Сортировка по умолчанию — «Закрыто», сначала недавние; дата закрытия
  ставится автоматически при переходе в архивный статус и очищается при
  возврате.
- «Вернуть в работу» — Админ/Суперадмин (5.5).

**Избранное.** Карточки как в «В работе» с фактическим этапом в углу;
единственное действие — «Перейти в карточку ↗».

**Календарь.** Сроки подачи, даты ожидания ответа, пункты чек-листа, задачи;
режимы День/Неделя/Месяц, боковая панель со списком; пользователь видит свои
события, Админ/Суперадмин — все [Решить: видимость для Руководителя отдела].

**Профиль.** ФИО, логин, роли, направления; смена пароля; личная статистика;
список тендеров пользователя; тема оформления.

**Платежи.** Площадки: название, ссылка, тариф, дата следующего платежа, счёт
и сумма обеспечения, комментарий. Смотрят все, редактируют Админ/Суперадмин.

**Настройки.**
- «Справочники»: направления (с цветом), причины отказа, решения, этапы

- «Роли и доступы»: матрица прав (Суперадмин).

  времени — по устройству пользователя или по Москве (см. раздел 12).
- «Автоматизация»: доступы к площадкам (логин, пароль, вход по ЭЦП),
  соответствие ключевых фраз отчёта ИИ пунктам чек-листа.

### 6.3. Карточка тендера

- **Шапка:** название (индикатор риска), заказчик (проверка Checko), НМЦ,
  у выигранного тендера — «Сумма договора» (см. ниже), отметка
  «Многолотовый», теги этапа тендера и этапа процесса, статус с кнопкой «Изменить», срок
  подачи (редактирование — по правам 3.3, с уведомлением участникам),
  готовность к подаче %, направления (пастельные теги), технические теги
  закупки.
- **Сумма договора:** выводится в одной строке с НМЦ через вертикальную
  черту — «НМЦ: … | Сумма договора: …» — и **только у тендера со статусом
  «Выиграли»**; у остальных строка содержит одну НМЦ. Ввод — карандаш →
  число → «Сохранить» (права — 3.3; остальным карандаш не показывается).
  Изменение пишется в журнал. По этой сумме дашборд считает «Выиграно на
  сумму».
- **Многолотовый тендер:** под строкой НМЦ — отметка «Многолотовый»
  (меняют Суперадмин, Админ, Менеджер, ответственный; у Наблюдателя —
  только просмотр). При отметке во вкладке «Обзор» появляется блок «Лоты»:
  таблица «Лот · Направление · НМЦ лота · Результат · Сумма договора» и
  итог «выиграно N из M»; редактирование через карандаш — добавить/удалить
  лот, выбрать направление и результат, сумма договора вводится только у
  выигранного лота. Сохранение пишет в журнал событие «Лоты обновлены: всего
  N, выиграно M, сумма договоров …». Строка «Сумма договора» в шапке у
  такого тендера считается по лотам и вручную не правится. Если отметку
  снять, блок скрывается, а данные лотов сохраняются и возвращаются при
  повторной отметке; сумма договора снова берётся из ручного поля.
  Пока у многолотового тендера нет выигранных лотов с суммой, его сумма
  договора пустая — ручное значение из шапки не подставляется (решено
  18.09.2026).
- **Правая панель:** постоянный список тендеров с фильтрами; не зависит от
  вкладки.
- **Вкладка «Обзор»:** описание закупки (редактируется), контактные данные,
  площадка (тип подачи; ссылка на закупку; площадка и обеспечение — если «На
  площадке»; адрес подачи КП — если «На почту»),
  отчёт и рекомендация ИИ (несколько версий, открыть последнюю, скачать,
  сгенерировать заново), комментарий менеджера, ответственные (менеджер и
  участники; редактирование по правам), прикреплённые документы. Состояние
  свёрнутых блоков сохраняется по тендеру для пользователя.
- **Вкладка «Этапы и заявки»:** признак «Многоэтапный»; этапы в хронологии;
  по каждому этапу — название, срок подачи, дата фактической подачи, сумма
  (без НДС, ставка, с НДС), заявки (срок, готовность), документы этапа, формы
  для заполнения, документы на подачу (выбор из Копилки, ZIP-скачивание),
  чек-лист документов («Сформировать лист», быстрое добавление); «Добавить
  этап» — после «Допущены»; завершённые этапы — только просмотр, кроме
  «Исправить» у Суперадмина (4.4).
- **Вкладка «Задачи»:** задачи по тендеру.
- **Вкладка «События»:** события после подачи (дата по умолчанию сегодня,
  текст).
- **Вкладка «Логи»:** журнал всех изменений, кроме сообщений чата.
- **Чат:** плавающая иконка в углу, доступен всем с доступом к тендеру;
  вложения — с устройства, из документов тендера, из Копилки.

### 6.5. Вход в сервис и восстановление пароля

Макет: `vhod.html`. **В макете проверки нет: кнопка «Войти» сразу открывает
дашборд.** Ниже — как это работает в рабочем сервисе.

**Экран входа.** По центру карточка: логотип «Тендеры · Атвинта», заголовок
«Вход в сервис», поля «Логин (email)» и «Пароль» (кнопка-глаз показывает
пароль), кнопка «Войти», ссылка «Забыли пароль?». Светлая и тёмная тема,
работает на телефоне.

**Вход:**

- логин и пароль проверяются на сервере, сессия серверная (2.1);
- при ошибке — одно общее сообщение «Неверный логин или пароль», без
  уточнения, что именно неверно, и без подсказки, есть ли такой пользователь;
- после 5 неудачных попыток вход по этому логину и с этого адреса блокируется
  на 15 минут; попытки и блокировки пишутся в журнал;
- деактивированный пользователь получает «Доступ отключён, обратитесь к
  администратору»;
- вход с временным паролем (выдал Админ) сразу ведёт на смену пароля, без неё
  сервис не открывается;
- после входа — дашборд или страница, которую пользователь пытался открыть;
- сессия заканчивается после 12 часов бездействия; при попытке действия —
  возврат на экран входа с сохранением адреса страницы;
- пароль не короче 10 символов, новый не совпадает с предыдущим; хранится
  только хэш (12).

**Восстановление пароля (ссылка «Забыли пароль?»):**

1. Пользователь вводит свой email.
2. Сервис всегда показывает одно и то же сообщение: «Если такой пользователь
   есть, мы отправили письмо со ссылкой» — чтобы нельзя было проверить
   наличие сотрудника в системе.
3. Письмо со ссылкой уходит на рабочую почту. Ссылка одноразовая и действует
   60 минут.
4. По ссылке пользователь задаёт новый пароль. После смены все его сессии
   на других устройствах завершаются, событие пишется в журнал.

**Если пароль потерял Суперадмин** (решение Оксаны 21.09.2026) — три пути,
в таком порядке:

1. **Сам по почте** — обычное восстановление по ссылке, как у всех.
2. **Второй Суперадмин** сбрасывает пароль и выдаёт временный. Поэтому
   правило: **в сервисе всегда не меньше двух Суперадминов** (Оксана
   Денисенко и Никита Долинин); при попытке снять роль у последнего
   Суперадмина сервис не даёт этого сделать и показывает предупреждение.
3. **Заявка разработчикам Атвинты** — крайний случай, если почта недоступна
   и второго Суперадмина нет. Пароль сбрасывается вручную на сервере после
   подтверждения личности заявителя, событие пишется в журнал; сотрудник
   входит по временному паролю и сразу меняет его.

Для писем нужен почтовый сервис (SMTP рабочей почты Атвинты или почтовый
провайдер) — настраивают разработчики при запуске.

## 7. Дашборд и статистика

### 7.1. Период

- Кнопки «С начала года», «С начала месяца», «Настроить период» (даты с–по).
- Всё считается на реальную текущую дату.

### 7.2. Главное правило подсчёта подач

Подача = **этап тендера с датой фактической подачи**. Подача попадает в
период по этой дате. **Текущий статус тендера на подсчёт подач не влияет**:
если по тендеру подали в апреле, а потом отклонили — апрельская подача
остаётся в статистике.

Вид подачи определяется этапом (решение 2026-09-17):

| Вид | Какие этапы | На дашборде |
|---|---|---|
| Подано первично | первый этап тендера, не считая ПКО/НДА перед ним (в т.ч. «Основной» после ПКО) | да |
| ПКО | этапы «ПКО» и «НДА» | нет (данные хранятся, на дашборд не выводятся) |
| Переторжки | этапы «Переторжка» (каждая отдельно) | да |
| Основной этап | этапы после первичной подачи, кроме переторжки («Этап 2», «Этап 3») | нет (данные хранятся, на дашборд не выводятся) |

«Подано всего» = «Подано первично» + «Переторжки».

**Выигрыши считаются по дате итога** (`result_date`), а не по дате создания
тендера: тендер, выигранный 09.07, попадает в июль, даже если создан в июне.
Дата итога проставляется автоматически, когда пользователь ставит итоговый
статус, и меняется при возврате из Архива. У перенесённых данных даты побед
взяты из примечаний листа «статистика»: 14.05, 15.05, 22.06 и 09.07.

### 7.3. Виджеты

Раскладка (макет `dashboard.html`): первый ряд — четыре плашки «Итоги
периода» и «По направлениям»; второй — «Статистика в динамике» и «Итоги по
этапам»; третий — «Причины отказов» и «Активные пользователи».

| Виджет | Что показывает |
|---|---|
| Получено новых | тендеры, созданные в периоде; строка «в т.ч. взяли на изучение» — новые тендеры периода, прошедшие первое решение (на рассмотрении, участвуем или отказ после начала работы); динамика |
| В работе | текущее состояние раздела «В работе» (не зависит от периода, без динамики); сумма НМЦ; строка «в т.ч. ПКО/НДА» |
| Подано | «Подано всего» (первично + переторжки) по датам фактической подачи; сумма НМЦ поданных тендеров; строки «в т.ч. первично», «переторжки», «ожидают ответа» (сейчас в статусе «Подано», кроме этапа ПКО/НДА) |
| Выиграно | выигрыши по дате итога; сумма договоров; если выигрыши есть, а сумм нет — надпись «сумма договоров не указана» (подсказка: сколько тендеров без суммы); список выигранных тендеров периода — название-ссылка на карточку, направление, сумма договора; динамика |
| По направлениям | переключатель Изучили / Подали / Выиграли; «Подали» — тендеры с первичной подачей в периоде; кольцевая диаграмма и легенда (кол-во, %, у «Выиграли» — сумма); тендер с несколькими направлениями учитывается в каждом |
| Статистика в динамике (бывш. «Воронка», «Статистика по этапам») | сглаженный график с заливкой по месяцам/дням: Новых получено, Взято в работу, Подано первично, Переторжки, Выиграно; режимы Количество / Сумма / Конверсия; при наведении — вертикальная линия и подсказка с периодом и всеми показателями; видимость линий настраивается (карандаш) |
| Итоги по этапам | таблица тех же показателей: кол-во, сумма, конверсия |
| Причины отказов | «Всего» с динамикой; горизонтальные полосы по причинам (решение «отказ») + отдельная полоса «Отказались после ПКО/НДА» (все тендеры со статусом «Отказались сами») |
| Активные пользователи | до 10 строк с прокруткой: сотрудник, число тендеров периода, где он ответственный или участник, сумма НМЦ; чекбокс «По ответственным» — считать только тендеры, где сотрудник ответственный |

**Динамика** — стрелка и процент изменения к периоду сравнения («к прошлому
месяцу», «к предыдущему периоду» или «к прошлому году»); если в периоде
сравнения значение было 0 — «новое». Не показывается, если в периоде
сравнения ещё не было данных. База сравнения выбирается в «Настроить»
радио-точками: «С таким же периодом прошлого года (год к году)» или
«С равным периодом текущего года (месяц к месяцу)» — второе по умолчанию;
настройка у каждого пользователя своя.

- **Многолотовые тендеры** (решено 18.09.2026): победа считается как
  **1 тендер**, даже если выиграно несколько лотов; «Выиграно на сумму» —
  сумма договоров выигранных лотов; в «По направлениям → Выиграли»
  учитываются только направления выигранных лотов (сумма направления —
  договоры его лотов); в списке выигранных — «лоты: 2 из 3». Подачи
  считаются как у обычного тендера — одна подача на все лоты.
- Виджеты можно скрывать/показывать («Настроить»); настройка — у каждого пользователя своя.
- Суммы выводятся с узкими пробелами между разрядами; тёмная тема
  поддерживается всеми виджетами, включая диаграммы.
- Выгрузка отчёта по дашборду (Word) с текущим периодом.
- Конверсия в «Итогах по этапам» считается от предыдущей строки, для
  «Переторжек» и «Выиграно» — от «Подано первично» (решено).
- Конверсия на графике «Статистика в динамике» считается по тому же правилу и
  **нарастающим итогом с начала периода**: точка месяца/дня = этап / база с
  начала периода по эту точку; последняя точка всегда равна значению в
  таблице. В подсказке к заголовку добавляется «· с начала периода».
  Конверсия может быть больше 100% (например, подач больше, чем взятых в
  работу за тот же период, — подачи считаются по дате подачи, «взято в
  работу» — по дате создания тендера).
- Подписи вертикальной шкалы не выводятся (решено 19.09.2026): остаётся
  сетка, значения — в подсказке при наведении.
- Линии сглаживаются **монотонно** (как `curveMonotoneX` в d3; решено
  19.09.2026): между двумя точками линия не выходит за их значения — не
  опускается ниже нуля и не рисует горб выше точки; вершина всегда в точке с
  реальным значением. Обычное сглаживание (через соседние точки) не
  использовать.
- Шкала графика — «круглый» шаг из ряда 1, 2, 5, 10, 20, 50…, не больше пяти
  делений; для количества и процентов шаг целый (не меньше 1), подписи не
  повторяются; конверсия до 100% — шкала 0–25–50–75–100%.
- Проверка при приёмке: сумма точек графика по каждому этапу (режим
  «Количество») равна строке таблицы «Итоги по этапам» за тот же период.

- Дано: новый пользователь с временным паролем. Когда: входит впервые.
  Тогда: сервис требует сменить пароль.

**Разделы и статусы**
- Дано: тендер в «Новых». Когда: «Взять в работу» с направлением и
  ответственным. Тогда: решение «на рассмотрении», тендер в «Ожидают
  решения», у ответственного задача и уведомление, запись в логах.
- Дано: тендер в «Заявках». Когда: Менеджер выбирает «Отклонено». Тогда:
  без причины сохранить нельзя; после выбора причины — окно «Тендер будет
  перенесён в раздел «Архив»»; до «Перенести» ничего не меняется; после —
  тендер в Архиве с датой «Закрыто».
- Дано: Менеджер, тендер «В работе». Когда: открывает смену статуса. Тогда:
  видны только ключевые статусы «В работе» и «Заявок» и сквозные для «В
  работе».
- Дано: архивный тендер. Когда: Админ возвращает его в «Заявки — подано».
  Тогда: решение «участвуем», статус «Подано», причина отказа очищена,
  «Закрыто» очищено, уведомление новому ответственному.

**Этапы и подачи**
- Дано: активный этап со статусом «Формирование заявки». Когда: пытаемся

## 14. Открытые вопросы

### До старта первой очереди

1. Выгрузка тендеров и отчёт ИИ — ответы специалиста (10.1): от них зависит,
   делать ли входной API уже в первой очереди.

### Ко второй очереди

2. Чат: создаётся ли стартовое сообщение-сводка при взятии тендера в работу.
3. Финансы по тендеру: нужно ли отслеживать оплату участия по конкретному
   тендеру (счёт, оферта, проверка, оплата, зачисление) или хватает раздела
   «Платежи» со справочником площадок.
4. Оценка трудозатрат: поле «вилка часов» в карточке или только через Jira.
5. Формирование КП (печать, подпись, скан) — действие в сервисе или вне его.
6. Связь «Ключей» Копилки с чек-листом: автоматический подбор документов ИИ.
7. Предпросмотр DOC/XLS, лимит размера файлов.
8. Полный список событий для уведомлений, прочитано/не прочитано, каналы вне
    сервиса.
9. Checko: источник ИНН, API или ссылка.
10. Jira: проект, типы задач, обратная синхронизация.
11. Онбординг новых пользователей.
